# 전략 검토 (냉정한 시각)

프로토타입 로직은 강하다(112 테스트, 응집된 엔진). 하지만 *제품*은 아직 아니고, 포지셔닝·UI·보안에 실존적 결정이 남아 있다. 아래는 아부 없는 검토.

## 1. 의도·목적 — 무엇을 만들고 있나

**강점:** 코어 IP는 진짜다. `당위 → 필연 하부구조 → 현실 데이터 착지 → 미착지 표면화`라는 grounding 엔진은 BI/OKR/컴플라이언스 툴과 구조적으로 다르다. "정직한 완료 정의(VERIFIED는 실제 이벤트 착지일 때만)"는 방어 가능한 차별점.

**위험 — 스코프 드리프트:** 이번 세션 동안 정체성이 다섯 번 이동했다.
```
SMB 제조 측정-착지 → 대표 리스크 레지스터 → 대표 경영관리 OS → 화이트리스트 행위게이트 → 30년 사례 taxonomy
```
각 이동은 개별적으론 정당했지만, 지금 제품은 *너무 많은 것*이 되려 한다. 엔진은 하나인데 표면이 사방으로 퍼졌다. **창업자는 팔 쐐기(wedge) 하나를 골라야 한다.** 세 후보의 buyer·sales motion·가격이 전부 다르다:
- (a) SMB 운영 디지털화 (측정 진실) — ROI 명확, buyer=공장장/대표
- (b) 대표 리스크·거버넌스 — buyer=이사회/오너, 판매 어려움
- (c) 대표 경영관리 OS — 비전은 좋으나 가장 붐비는 시장(모든 것과 경쟁)

**판정:** 비전은 (c)로 두되, GTM은 (a)로 시작해야 한다(아래 근거).

## 2. 시장 포지셔닝 feasibility

**대표 리스크·거버넌스를 SMB에 콜드로 파는 건 어렵다:**
- SMB 대표는 "리스크 관리"를 *grudge purchase*(마지못한 지출)로 본다. 돈 벌거나 눈에 보이는 비용·시간 아끼는 걸 산다.
- 예방 가치가 반증 불가("사고가 안 났다"는 증명이 안 됨) → 갱신 논리 약함.
- 거버넌스의 진짜 buyer는 종종 이사회/오너지 *운영* 대표가 아니다.
- 오너리스크·갑질·탱크데이 앵글은 PR·바이럴엔 최고지만 **에피소드성**이다(스캔들 직후만 관심).

**가장 feasible한 쐐기:** 원래의 것 — **"당신은 X를 측정한다고 믿지만 실은 아니다"**(운영 진실). 한 업종(사출/CAMS)에서 ROI가 손에 잡힌다. 리스크·거버넌스는 *확장*으로 얹어라, 첫 판매로 팔지 말고.

**긴장 하나:** "한 업종 깊게(Kind-B 분할상각)" vs "전 산업 대표 거버넌스(최근 추가분)"는 상충한다. 오너리스크는 크로스산업, 측정엔진은 버티컬 깊이. **둘 다 못 한다 — 초기엔 버티컬 깊이를 택해라.**

## 3. 서비스 구성

**강점:** 파이프라인이 응집적이고 테스트됨. grounding→category→cascade→manage→track 루프는 구조적으로 건전.

**약점(정직히):** 전부 CLI/라이브러리 + 정적 HTML이다. **아직 제품이 아니라 로직의 잘 짜인 프로토타입.** 하드한 부분이 스텁이다:
- 실제 ERP/MES/현장에서의 *증거 수집 파이프라인*(콜드스타트 (i))이 어댑터 껍데기뿐
- 지속성이 JSON 파일 하나, 멀티유저·인증·권한 없음
- **템플릿(Kind-B)이 수작업 시드** — "분할상각"은 템플릿 저작이 스케일해야 성립하는데, 지금은 전문가(당신) 병목. 이게 진짜 확장 병목이고 미해결.

## 4. UI — 대표가 쓰기 편한가

**정직히: UI가 없다.** CLI + 생성 HTML이다. **대표는 CLI를 절대 안 쓴다.** HTML 보드/대시보드는 방향은 맞다(1페이지, 인쇄, 순위) — 하지만 정적 산출물이지 인터랙티브 제품이 아니다.

**대표용 UX 원칙(설계 지침):**
- **입력 최소화.** 대표는 폼을 혐오한다. 조직도·증거 입력은 *직원/연동*이 하고, 대표는 오직 *조타*(select/delegate)만.
- **"검토하고 결정"이 주 인터랙션.** "지금 볼 3개 + 왜 지금" → 원탭 선택/위임.
- **모바일 우선.** 대표는 폰에 산다.
- 우리 select→cascade→manage 루프는 *좋은 대표 UX에 그대로 매핑된다* — 앱으로 지으면. 지금은 그 로직만 있고 표면이 없음.

**권고 최소 제품:** (1) 주기적 1페이지 브리프(메일/모바일: "주의 필요 3건 + 왜"), (2) 원탭 선택·위임, (3) 궤적 대시보드. 대표 타이핑 제로.

## 5. 보안 — confidential 데이터 (가장 중요, 실존적)

**당신 지적이 100% 옳고, 이건 나중에 붙일 기능이 아니라 *지금* 내려야 할 아키텍처·포지셔닝 결정이다.**

대표가 회사의 *약점·은닉 리스크·임원 비위·핵심가치*를 무료 웹서비스에 입력하는 건 시작 불가다. 이 데이터는 대부분 데이터보다 민감하다 — 문자 그대로 "우리 회사 취약점과 내 개인 책임 노출." 유출은 파국이고, **불안하다는 *인식*만으로도 대표 레벨 채택이 죽는다.**

옵션(냉정한 평가):

| 방식 | 신뢰 | 편의 | 평가 |
|---|---|---|---|
| **A. 로컬 우선(local-first)** — 엔진이 고객 머신/서버에서 돌고 민감 데이터가 안 나감 | ★★★ | ★★ | **최선.** 이름(`SelfDeploy`)이 이미 이걸 말함. 엔진이 이미 오프라인-결정론 기본이라 *바로 됨* |
| **B. 온프렘/VPC 커스텀 배포** — 고객 클라우드에 별도 DB로 | ★★★ | ★ | 큰/보수적 고객용 프리미엄. 당신이 말한 "별도 서비스" |
| **C. E2E 암호화 SaaS(zero-knowledge)** — 클라 암호화, 서버는 암호문만 | ★★ | ★★ | 편의 유지하나 서버측 연산 제약, 정확히 짓기 어려움 |
| **D. 무료 웹서비스에 업로드** | ✗ | ★★★ | **절대 금지.** 이 데이터로는 안 됨 |

**강력 권고: 로컬-우선을 기본이자 브랜드로.** 이유:
1. **이름이 이미 그것이다** — `SelfDeploy` = 당신이 직접 배포.
2. **아키텍처가 이미 그렇다** — 결정론 코어는 네트워크 호출이 없다(LLM만 선택적 아웃바운드). "당신 리스크 데이터는 건물 밖으로 안 나갑니다"를 *지금 진실로* 말할 수 있다 — 어떤 SaaS 경쟁자도 못 하는 신뢰 우위.
3. **포지셔닝 긴장까지 해소** — "SelfDeploy = 당신이 직접 굴리는 리스크·경영 엔진, 데이터는 안 나감"은 대표가 실제로 yes 할 수 있는 선명한 신뢰-우선 포지션.

**구체 실행:**
1. 결정론 코어를 *증명 가능하게 network-free*로(이미 그러함 — 문서·테스트로 보증).
2. 모든 선택적 아웃바운드(LLM)를 명시 플래그 + **데이터 최소화·레닥션** 뒤로(예: 캠페인 문자열만 보내지 리스크 포트폴리오 전체 금지). 또는 로컬 모델 옵션.
3. `state.py` 포트폴리오·증거를 **at-rest 암호화** 로컬 파일로.
4. 배포를 고객이 굴리는 **단일 바이너리/컨테이너**로.
5. 편의 원하는 곳엔 **호스팅 티어 = 테넌트별 격리 + 암호화 DB**를 별도 프리미엄으로.
6. 무료/오픈 경로 = "직접 돌려봐, 아무것도 전화 안 함" → 리드젠.

## 종합 판정

- **IP:** 진짜. grounding 엔진 + 정직한 완료정의 + 30년 사례 근거 카테고리.
- **제품:** 잘 설계된 프로토타입, 아직 서비스 아님(수집·멀티유저·UI·템플릿 저작 스케일이 미해결).
- **1순위 결정:** 보안·배포 모델 = **로컬-우선**(이름·아키텍처와 정렬, 신뢰 우위). 이게 정해지면 나머지가 따라온다.
- **GTM:** 한 버티컬 운영-진실 쐐기로 시작, 리스크·거버넌스는 확장. "대표 리스크 OS"를 콜드로 팔지 마라.
- **UI:** 대표 타이핑 제로 + 모바일 1페이지 브리프 + 원탭 조타. 지금 로직은 맞고 표면이 없다.
